1. HOW pandas .plot AND plt ARE CONNECTED
------------------------------------------
- pandas .plot uses matplotlib as its backend engine.
- When pandas draws a chart (.plot.barh(...)), it automatically becomes
  the "current active figure" in matplotlib's global state.
- plt (matplotlib.pyplot) functions like plt.title(), plt.ylabel(),
  plt.xlabel() then act on that same active figure — no reference needed.
- This is called the Implicit Global State Machine pattern.
- Without "import matplotlib.pyplot as plt", the .plot() still works
  but plt.title() etc. crash with NameError: name 'plt' is not defined.

Coding Patterns used:
  - Facade Pattern: pandas .plot hides complex matplotlib code behind a simple one-liner.
  - Global State Machine: plt always modifies the last active figure automatically.
  - Separation of Concerns: pandas handles data, matplotlib handles appearance.


2. axis=1 IN data.apply()
---------------------------
  data['tokenized'] = data.apply(lambda x:
                                  word_tokenize(
                                  x['review_no_stopwords_no_punct']
                                  ), axis=1)

- apply() runs a function on every row or column of a DataFrame.
- axis=0 (default) = apply function to each COLUMN (travels top to bottom).
- axis=1 = apply function to each ROW (travels left to right).
- With axis=1, x represents one full row, so x['column_name'] picks
  the value from that column in that specific row.
- word_tokenize() splits the text string into a list of word tokens.
- The backslashes (\) are line continuation characters — the code is
  one logical line split across multiple lines for readability.

4. TIME & SPACE COMPLEXITY OF N-GRAM CALCULATION
--------------------------------------------------
Variables:
  N = total number of tokens
  n = gram size (1=unigram, 2=bigram, 3=trigram)
  V = number of unique n-grams (vocabulary size)

Time Complexity:
  - Generating n-grams (nltk.ngrams):   O(N x n)
  - Counting frequencies (value_counts): O(N x n)
  - Sorting (sort_values):               O(V log V)
  - TOTAL:                               O(N x n + V log V)
  - For small fixed n (1,2,3) this simplifies to O(N)

Space Complexity:
  - Raw n-grams Series:    O(N x n)
  - Frequency count dict:  O(V x n)
  - TOTAL:                 O(N x n)

Practical note:
  - nltk.ngrams is a lazy generator (does not store all n-grams in memory).
  - pd.Series() forces materialization into memory.
  - For large corpora, large n values are expensive and cause data sparsity
    (most n-grams appear only once). This is why n is typically kept <= 3.

========================================================
Text Tagging (Sequence Labeling)
========================================================

Overview:
  - Text tagging assigns a label to each token (word) in a sentence — or to a span
    of tokens — based on its role in the text.
  - Also called sequence labeling: input is a sequence of words, output is a sequence
    of tags (one label per token, or start/end tags for multi-word spans).
  - Two main types in this course:
      1. POS Tagging      — grammatical role (noun, verb, adjective, ...)
      2. NER              — real-world entity type (person, org, location, date, ...)
  - Example (POS):
      "Google"  → PROPN (proper noun)
      "founded" → VERB
      "1998"    → NUM
  - Example (NER):
      "Larry Page" → PERSON
      "Google"     → ORG
      "California" → GPE
  - Usually runs after tokenization; spaCy does tokenization + POS + NER in one pipeline.
  - Pre-trained models (spaCy en_core_web_sm, NLTK, BERT) tag text without manual rules.

Pros:
  - Adds linguistic structure to raw text — grammar and meaning become machine-readable
  - Enables smarter downstream NLP (lemmatization needs POS; search needs entities)
  - Pre-trained taggers work out of the box on general English
  - Same pipeline pattern for POS and NER — learn one, apply both
  - Improves accuracy of parsing, sentiment, and information extraction vs raw text alone
  - Tags can be used as features for ML models (e.g. only keep nouns/adjectives)

Cons:
  - Taggers trained on news/general text fail on slang, typos, and domain jargon
  - Ambiguous words get wrong tags without full sentence context ("book" noun vs verb)
  - POS and NER errors compound — bad tokenization → bad tags → bad entities
  - Domain-specific tasks (medical, legal) often need custom models or fine-tuning
  - Multi-word entities and nested structures are harder than single-token POS tags
  - Language-specific — English models do not transfer well to other languages

Use Cases:
  - Text preprocessing — POS helps lemmatization pick correct word form (noun vs verb)
  - Grammar checkers and writing assistants — detect wrong word usage
  - Search & indexing — filter by nouns, entities, or key phrases
  - Chatbots — understand sentence structure before generating a reply
  - Information extraction pipelines — POS + NER as first stage before relation extraction
  - Feature engineering — use tags as input to classifiers (spam, sentiment, intent)
  - Document understanding — resumes, contracts, news articles

========================================================
Named Entity Recognition (NER)
========================================================

Overview:
  - NER is a type of text tagging that finds and classifies named entities in text —
    real-world objects referred to by name (people, companies, places, dates, etc.).
  - Unlike POS (grammar), NER extracts semantic "who / what / where / when" from text.
  - Tags apply to spans of tokens, not just single words:
      "Stanford University" → ORG
      "September 4, 1998"     → DATE
      "Sundar Pichai"         → PERSON
  - Common spaCy labels: PERSON, ORG, GPE, DATE, TIME, MONEY, PERCENT, PRODUCT, EVENT
  - Typical workflow (from 3.3 NER notebook):
      import spacy
      nlp = spacy.load('en_core_web_sm')
      doc = nlp(text)
      for ent in doc.ents:
          print(ent.text, ent.label_)
  - Output: structured fields extracted from unstructured text.

Pros:
  - Automatically pulls names, dates, places, and organizations from documents
  - Fast with pre-trained spaCy/transformer models — minimal setup
  - Powers search, filtering, and auto-categorization without manual reading
  - Foundation for knowledge graphs, relation extraction, and QA systems
  - Reduces manual data entry (forms, invoices, resumes, support tickets)
  - Cleaning text (lowercase, punctuation) can improve or change tagging results

Cons:
  - Misses domain-specific entities (drug names, legal clauses, product SKUs)
  - Ambiguity — "Apple" (company vs fruit), "Washington" (person vs city vs state)
  - Wrong labels on abbreviations and informal text (e.g. "PhD" → WORK_OF_ART in demo)
  - Does not extract relationships — only identifies entities, not how they relate
  - Nested entities are hard ("University of California, Berkeley")
  - Custom entity types require training data and fine-tuning
  - Performance varies by language, dialect, and text quality

Use Cases:
  - Resume parsing — extract candidate name, employers, skills, education, dates
  - News & media — auto-tag people, organizations, locations in articles
  - Customer support — route tickets by company, product, or location mentioned
  - Healthcare — identify diseases, drugs, symptoms in clinical notes
  - Finance & compliance — extract companies, amounts, dates from reports
  - Search — "hotels in Paris" or "reviews mentioning Tesla"
  - Chatbots — slot filling: "Book a flight to [GPE] on [DATE]"
  - Social media monitoring — track brand names and locations in posts
  - PII detection — find names, addresses, IDs for redaction in documents
  - Knowledge graphs — populate entity nodes from raw text


========================================================
1. Vectorizing Text
========================================================

What it is:
  - Converting text (words, documents) into numerical vectors so ML models
    can process them. Computers can't train on raw strings — they need numbers.
  - Output is usually a matrix: rows = documents, columns = features (words or
    dimensions). Each cell is a score (count, weight, or embedding value).
  - Methods range from simple (Bag of Words, TF-IDF) to dense embeddings
    (Word2Vec, GloVe, BERT).

Pros:
  - Makes text usable for classifiers, clustering, similarity search, etc.
  - Many methods are fast, interpretable, and easy to implement (sklearn)
  - Foundation for almost every classical NLP ML pipeline

Cons:
  - Simple methods lose word order and meaning context
  - Sparse vectors can be huge (vocabulary size = number of dimensions)
  - Choice of method strongly affects downstream model quality

Use cases:
  - Document classification (spam, sentiment, topic labels)
  - Search / similarity (find related reviews or articles)
  - Clustering documents, recommendation, feature input to any ML model

When to use:
  - Anytime you need to feed text into a machine learning model
  - Start with BoW/TF-IDF for baselines; move to embeddings when you need
    semantic meaning or better accuracy on nuanced language

========================================================
2. Bag of Words (BoW)
========================================================

What it is:
  - Represents a document as a count (or presence) of each word in a fixed
    vocabulary — order is ignored ("bag" = unordered multiset of words).
  - Example: vocab = [cat, dog, sat]
      "the cat sat" → [1, 0, 1]
      "dog dog cat" → [1, 2, 0]
  - Built with CountVectorizer (sklearn) after tokenization / preprocessing.

Pros:
  - Simple, fast, highly interpretable (each dimension = a word)
  - Strong baseline for many text classification tasks
  - No pre-trained model needed — works from your corpus alone

Cons:
  - Ignores word order and grammar ("not good" ≈ "good not")
  - Treats all words equally — common words can dominate rare meaningful ones
  - Sparse, high-dimensional; vocabulary grows with corpus size
  - Synonyms ("car" vs "automobile") are unrelated dimensions

Use cases:
  - Spam detection, intent classification, simple sentiment baselines
  - Quick feature extraction before logistic regression / Naive Bayes / SVM
  - Exploring word frequency patterns in a corpus

When to use:
  - Small/medium corpora and classical ML baselines
  - When interpretability matters (which words drive the prediction)
  - Prefer TF-IDF over raw BoW when common words drown out signal

========================================================
3. TF-IDF (Term Frequency–Inverse Document Frequency)
========================================================

What it is:
  - A weighted version of Bag of Words.
  - TF (Term Frequency) = how often a term appears in a document
  - IDF (Inverse Document Frequency) = down-weights terms that appear in
    many documents (e.g. "the", "hotel") and boosts rarer, more distinctive terms
  - Score ≈ TF × IDF — high when a word is frequent in this doc but rare overall
  - Built with TfidfVectorizer (sklearn)

Pros:
  - Better than raw BoW at highlighting distinctive words
  - Still sparse, interpretable, and fast
  - Excellent default vectorizer for classical text ML
  - Reduces impact of stopwords even if you didn't remove them all

Cons:
  - Still ignores word order and semantics
  - Synonyms remain separate features
  - Can underweight important but frequent domain terms (e.g. "room" in hotel reviews)
  - Sparse matrices still get large with big vocabularies

Use cases:
  - Document classification and ranking
  - Keyword extraction / finding characteristic terms per document
  - Search engines (classic relevance scoring)
  - Input features for sentiment, topic labels, clustering

When to use:
  - Default choice after BoW for most classical NLP pipelines
  - When you care which words make a document unique vs the whole corpus
  - Before upgrading to embeddings if BoW underperforms due to common-word noise

========================================================
4. Topic Modeling and LDA
========================================================

What it is:
  - Topic modeling: unsupervised method to discover latent "topics" in a
    collection of documents (themes that emerge from word co-occurrence).
  - Each topic is a distribution over words (e.g. Topic A: hotel, room, staff;
    Topic B: food, restaurant, menu).
  - Each document is a mixture of topics (e.g. 70% Topic A, 30% Topic B).
  - LDA (Latent Dirichlet Allocation): the most common generative probabilistic
    topic model. Assumes documents are generated by sampling topics, then words
    from those topics. Uses Dirichlet priors over topic and word distributions.
  - Input is usually BoW or TF-IDF counts; output is topics + document-topic weights.

Pros:
  - Unsupervised — no labeled data required
  - Interpretable topics (lists of top words per theme)
  - Useful for exploring and summarizing large text corpora
  - Documents get soft topic mixtures (not forced into one category)

Cons:
  - Number of topics (K) must be chosen / tuned
  - Topics can be noisy, overlapping, or hard to name
  - Assumes bag-of-words (ignores order); sensitive to preprocessing
  - Not as strong as supervised classifiers when labels exist
  - Results can vary with randomness / hyperparameters

Use cases:
  - Discover themes in reviews, news, research papers, support tickets
  - Content organization / tagging without predefined categories
  - Exploratory analysis before building a labeled classifier
  - Recommendation and content browsing by theme

When to use:
  - Large unlabeled corpora where you want to discover themes
  - When categories are unknown or too expensive to label manually
  - Prefer supervised models (or embeddings + clustering) if you already have
    clear labels or need precise classification accuracy
  - Use LDA for interpretable classical topic discovery; consider BERTopic /
    neural topic models when you need stronger semantic coherence
